Canonical guide for all coding agents (Claude Code, Codex, OpenCode, Pi, …). `CLAUDE.md` imports this file — edit here, not there.

The Dockerfile is multi-stage and installs the locked dependencies with `uv sync --locked` (from `uv.lock`).

```bash
ruff check . --fix && ruff format .

pre-commit run --all-files        # whitespace/yaml/toml checks, ruff (--fix --unsafe-fixes), ruff-format, mypy, pytest
```

**Tests** — unit and PostgreSQL integration tests; unit tests need no DB or network (DB, bot, interaction and context are mocked in `tests/conftest.py`). `tests/test_schema_postgres.py` is skipped unless `VEKA_TEST_DATABASE_URL` points at an **empty, disposable** PostgreSQL database (its `public` schema is dropped); it applies every migration with the real runner and `prepare()`s every static SQL string in `src/`. ## Architecture

- **Entrypoint:** `main.py` → `src/core/app.py:run_bot()` → loads `.env`, `setup_logging()`, `build_bot()`, registers events, loads extensions, `bot.run()`.
- **Startup (`on_ready`, guarded to run once):** set `bot.notifier` → `initialize_database()` (connect, then `db.run_migrations()`) → `StartupChecks.run_all_checks()` (`src/core/checks.py`) → `bot.notifier.send_startup_summary()` → `db_health_check.start()` (30s loop; while the DB is up it also calls `recover_after_db_available()` — deferred migrations + retry of failed `cog_ready` hooks) → `run_cog_ready_hooks(bot)` (each cog's `cog_ready()`) → logs `"<bot> is ready. DB available=<bool> migrations=<ok|degraded>"` (the deploy greps this line) → `bot.sync_all_application_commands()`.
- **Extensions load from an explicit allowlist** — `EXTENSIONS` in `src/core/app.py` (24 entries, dotted `src.cogs.*` paths; disabled cogs are left in as comments). A cog not in the list is not loaded; add it there to enable it. Every cog module needs a module-level `setup(bot)`; slash groups use `nextcord.SlashCommandGroup`.
- **Layers:** `src/cogs/` (thin Discord handlers) → `src/services/` (business logic) → `src/database/` (data access).
- **Intents:** `message_content`, `members`, `guilds`, `voice_states`, `presences`.

### Degraded mode (central design theme)

The bot keeps running when the DB, a cog, or a background task fails:

- `src/core/runtime_state.py` — global `runtime_state` dataclass (attached as `bot.runtime_state`): `db_available`, `loaded_cogs`, `failed_cogs`, `degraded_features`, `startup_check_results`, `alert_state_cache`, `last_db_error`, `last_recovery_time`. Source of truth for health/observability.
- DB connect failure at boot → `db_available=False`, `'database'` added to `degraded_features`; boot continues. Migration failure → `'migrations'` degraded, DB stays available.
- `db_health_check` (`@tasks.loop(seconds=30)`) pings the DB, flips `db_available`, and alerts admins on lost/recovered transitions.
- Per-extension load failures are recorded in `failed_cogs`; other cogs still load.

### Database

- Global singleton `from src.database.database import db`. **`$1`/`$2` parameter style.**
- Methods: `fetch`, `fetch_one`/`fetchrow`, `fetchval`, `execute`, `execute_many` (all via `Database._run`). Connection-class failures (incl. `OSError`/timeouts) raise `DatabaseUnavailableError` and flip `runtime_state.db_available = False`; SQL errors raise `DatabaseQueryError` (a subclass, so `except DatabaseUnavailableError` still catches it) and leave the DB marked available. Only argument *types* are logged, never values; PostgreSQL errors are summarized by `_describe_pg_error` (class, SQLSTATE, table/column/constraint; primary message dropped for SQLSTATE classes `22`/`P0`) and never chained, because `str(exc)` includes `DETAIL` with row values. Pool has `command_timeout=30s`. Never assume a query succeeded.
- Connection pool strips libpq-only keepalive params (`keepalives`, `tcp_keepalives_*`) that PostgreSQL would reject as unknown server settings.
- **Migrations:** `.sql` files in `migrations/` (001–039; no `002`; `005_` and `005b_` coexist — the duplicate check compares the full prefix incl. letter suffix), applied in filename order on connect, tracked in `schema_migrations` by filename. **Never rename an applied migration**; if you must, add the old name to `LEGACY_MIGRATION_NAMES` in `src/database/migrations.py` (as for `005b`). Add new ones as `migrations/0NN_name.sql` with the next unused number. Make them idempotent (`IF NOT EXISTS`, guarded `DO $$` blocks) and use `TIMESTAMPTZ DEFAULT NOW()`. Discord IDs are `BIGINT`; `users.id` is an internal serial PK — don't mix them.

### Per-guild settings

Channel/role config is per guild in the `guild_settings` table, read via `from src.services.guild_settings_service import guild_settings_service` (`get_settings`, `update_settings`, `invalidate_cache`, `resolve_channel`; in-memory cache). Configured by staff with `/setup` / `!setup` (`src/cogs/admin/setup.py`). Server channels have no config/env fallbacks; resolve them through the service. `ADMIN_ALERT_CHANNEL_ID` remains a bot-operator operational alert destination, not a server feature channel.

### Per-guild modules

`src/services/module_registry.py` defines feature IDs and UI metadata; `guild_modules` (migration 038) stores disabled IDs and a monotonic version. Core/settings/privacy are locked on. Activity off stops collection; leveling off keeps counts but awards no XP; dependencies are declared without automatic toggles. The bot applies global prefix/application checks and guild gates to automation, with a bounded TTL cache, `modules:<guild_id>` NOTIFY invalidation and full-reset recovery. Unknown state fails closed for automation and commands report temporary unavailability (not an admin disable); outages retain last-known switches. Disabled bulk-unban workers pause; configuration, reads and privacy remain available. GET/PATCH `/v1/guilds/{id}/modules` use Manage Server, fresh write auth, strict booleans, required `If-Match`, transactional audit/NOTIFY, and string versions. `/v1/meta` exposes least-privilege invite permissions. Guild overview returns `bot_status`, permission `diagnostics` and aggregate `command_usage_7d`. Settings GET/PATCH include policy-derived `schema` metadata.

### Dashboard API (`src/api/`)

FastAPI service for the web dashboard, **separate process** (`python -m src.api`; compose service `api` → container `veka-api` in production, deployed and health-checked by `deploy.yml`, no host port: joined to the external `proxy-network` and routed by Traefik labels (`api.veka.gg`, `internal-only`) — deploy notes in `README.md`; dev compose service `api`, image built with `--build-arg UV_EXTRAS="--extra api"`; FastAPI/uvicorn live in the optional `api` extra, not in the bot image). It never imports cogs and connects the shared `db` singleton (one pool per process; `_keep_db_connected` retries until up). Contract:
- **Auth** (`auth.py`): users send `Authorization: Bearer <Discord OAuth token>` (scopes `identify guilds`); the API verifies it with Discord (`discord_client.py`, `/users/@me` + paginated `/users/@me/guilds`, 5 s timeout, cached 60 s by token SHA-256; privileged writes use `fresh=True`). Discord 401 → 401; 429/5xx/network → 503. `X-Service-Token` is a separate *service* principal accepted only where a route passes `allow_service=True`; `X-Acting-User` is audit metadata, never identity. Pre-auth per-IP and per-client token buckets (`ratelimit.py`, in-process, single replica). Behind `API_TRUSTED_PROXIES` (IPs/CIDRs) the client IP is the right-most untrusted `X-Forwarded-For` hop.
- **Guild access** (`guild_access(*bits)`): the user's Discord permissions in that guild (owner/Administrator imply all) **and** a fresh `bot_guild_snapshot` row (bot present). **Manage Server is required for every guild route**; some actions need an extra permission on top: Manage Roles for role settings, Ban/Kick/Moderate Members for warnings and the moderation audit log, Ban Members for mass unban. Owner-only data (`/v1/me/*`) is never reachable through guild rights. Every nested `/{id}` checks `guild_id` (IDOR).
- **Envelope** `{"error": {"code", "message", "details"}}` for every failure (`errors.py`); snowflakes are strings in JSON; keyset pagination `?limit=&cursor=` → `{items, next_cursor}` (`pagination.py`); bodies ≤ 64 KB counted on the wire; OpenAPI at `/v1/openapi.json` + `/v1/docs` unless `ENVIRONMENT=production` (set `API_DOCS=1` to keep).
- **Writes** run in `db.transaction()` (new helper; errors mapped like single queries): the change, an `audit_logs` row (`source: dashboard`) and `pg_notify('veka_cache', '<kind>:<id>')` commit together. Settings use `If-Match: <version>` (412 on conflict), strict types, policy from `src/services/guild_settings_policy.py` (shared with `/setup`), snapshot-validated channel types and safe muted roles (no privileged bits, below the bot).
- **Bot side:** `src/cogs/admin/api_bridge.py` writes `bot_status` (every minute) and `bot_guild_snapshot` (channels, roles with permission bits, counts, bot top-role position; every 5 min and within a minute of a change; deleted on guild leave). `src/core/cache_listener.py` holds `LISTEN veka_cache` and applies `guild_settings` / `honeypots` / `privacy` / `massunban` invalidations sequentially from a coalescing queue; on connect, on handler failure (with backoff) and every 5 min it runs a full reset, so a lost NOTIFY heals.
- **Mass unban from the dashboard:** `POST /jobs` → `requested`; the bot claims it (CAS, `claimed_at`), lists bans, freezes the matched items and counts in one transaction → `awaiting_confirmation`; `confirm` step 1 returns a single-use token (only SHA-256 stored, 5 min), step 2 needs that token + the exact count from the same requester → `running`, and the bot starts the normal worker. Cancel works for Discord- and dashboard-started jobs. Stuck previews requeue after 10 min; the bot reconciles every 5 min.
- Routes: `/v1/health` (always 200, reports db/bot status), `/v1/ready` (200 / 503 when the DB is unreachable; used by Docker, Traefik and the deploy), `/v1/me`, `/v1/me/guilds`, `/v1/me/privacy` (GET/PUT), `DELETE /v1/me/activity`, `/v1/guilds/{gid}` (+`/channels`, `/roles`), `/v1/guilds/{gid}/settings` (GET/PATCH), `/warnings` (+`/{id}/revoke`), `/audit-log` (typed, redacted), `/massunban/jobs` (+`/{id}`, `/confirm`, `/cancel`), `/honeypots` (+`/{id}`, `/events` without message content, `/logging`; permission follows the trap's action, checked on the locked row), `/feeds` (+`/{id}`, `/{id}/test` preview, never posts; quota via `src/services/feed_service.py` under an advisory lock shared with `/feed add`), `/leaderboards?category&period` and `/members/{uid}/activity` (per server; shared queries in `activity_service`), `/stats/daily?from&to` (≤366 days), and the marketplace endpoints (Pi, `src/api/routes/marketplace.py`). Mass-unban creation (Discord and API) takes the same per-guild advisory lock; preview claims are fenced by `claimed_at`; terminal writes never overwrite `cancelled`; the worker re-reads the persisted status before every unban.
- Env (API process only, all optional for the bot): `API_SERVICE_TOKEN`, `API_CORS_ORIGINS`, `API_RATE_LIMIT`, `API_PREAUTH_LIMIT`, `API_TRUSTED_PROXIES`, `API_DOCS`, `API_HOST`/`API_PORT`, `DISCORD_API_BASE`.

## Conventions

- **Dual command surface:** features define both a `!`-prefix command (prefix hardcoded in `src/config/config.py`) and a slash command, usually side by side in the same cog. Keep both in sync.
- **Safety wrappers** (`src/utils/safety.py`): `@safe_command(requires_db=True)` / `@safe_slash_command(requires_db=True)` short-circuit when the DB is down, catch and log unexpected exceptions, and reply with an error embed. `safe_send(target, ...)` handles both `Context` and `Interaction` (responded or not) — prefer it over `ctx.send` / `interaction.response`. `@safe_background_task(name=...)` wraps `@tasks.loop` bodies and alerts admins after ≥3 consecutive failures.
- **Domain exceptions** `DatabaseUnavailableError`, `ValidationError`, `ExternalRequestError` are mapped to user messages centrally (`_handle_command_error_common` in `app.py`, `map_exception_to_message`).
- **Embeds** (`src/utils/embeds.py`): all user-facing output uses `veka_embed`, `success_embed`, `error_embed`, `info_embed`, `alert_embed`. Pass `contributor_source=__name__` so the footer attribution resolves via `_STATIC_CONTRIBUTOR_MAP` (keyed by full module path).
- **Security** (`from src.utils.security import ...`): `rate_limit('bucket')`, `InputValidator`/`sanitize`/`validate_id`/`is_safe`, `audit_log`/`audit_action`, and RBAC `require_verified`/`require_staff`/`require_mod`/`require_admin`/`require_founder`. Role hierarchy: USER < VERIFIED < INTERN < DONATOR < ACTIVE_PRO < STAFF < ADMIN < FOUNDER; `require_mod()` is an alias for `require_staff()`. RBAC decorators work for both prefix and slash commands.
- **Two parallel auth systems (intentional):** `admin_only()`/`staff_only()`/`manage_guild_only()`/`bot_operator_only()` in `safety.py` (ID lists + Discord permissions) and the RBAC `require_*` decorators (role names). Don't consolidate.
- **Slash-command permission checks:** nextcord **ignores `commands.check` on application commands**. Every guard must go through `permission_guard(predicate, message)` in `safety.py` (all the decorators above and `guild_gate.main_server_only`/`owner_in_external_only` do). Put guards directly under `@slash_command`/`@subcommand`. Add privileged commands to `PRIVILEGED_SLASH_COMMANDS` in `tests/test_permissions.py`. Bot-wide actions (reloading code, global settings) use `bot_operator_only()`.
- **Channels are resolved inside the invoking guild only** (`guild_settings_service.resolve_channel(guild, ...)` / `guild.get_channel`). Never `bot.get_channel(<config fallback>)` from a guild-scoped path — that posts into the main server from other servers.
- **Outbound messages** (`src/utils/outbound.py`, `outbound` / `bot.outbound`): every bot-initiated message that isn't a direct reply to the invoking user goes through `outbound.send(channel, kind=…)`, `outbound.dm(user, kind=…)`, `outbound.create_thread(forum, kind=…)` or `outbound.upsert_status(key, channel, …)`. It enforces per-channel/guild/global and (tighter) DM token buckets, de-duplicates identical messages within a window (attachments only with an explicit `dedupe_key`), honours `retry_after` once, and opens a circuit breaker after repeated 429/403/50007 that pauses non-essential sends (and DMs separately) and alerts admins once. `essential=True` only for things the user asked for or admins must see. `dm()` refuses users who share no guild with the bot. Progress/status updates edit one message (`upsert_status`), never post per event. Unsolicited DMs are opt-in (mass-unban apology per job, inactivity per guild). Use `TTLDict` (`src/utils/ttlcache.py`) for cooldowns/caches instead of plain dicts.
- **Mentions:** the bot defaults to `AllowedMentions(everyone=False, roles=False)`. A send that must ping a role or @everyone passes `allowed_mentions=` explicitly, and the mention goes in `content` (mentions inside embeds never notify).
- **Logging:** `logging.getLogger('VEKA.<area>')` or `get_logger('VEKA.<area>')` from `src/utils/logger.py`. Rotating file handler (5 MB × 3); level from `LOG_LEVEL`.
- **Time:** use `datetime.now(UTC)`, never `utcnow()`.
- **Background work:** use `spawn(coro, name=...)` from `src/core/lifecycle.py` (keeps a reference, logs exceptions) — never bare `asyncio.create_task`/`ensure_future`. Callbacks from other threads (e.g. voice `after=`) must use `asyncio.run_coroutine_threadsafe(coro, bot.loop)`.
- **Cog lifecycle (nextcord ≠ discord.py):** nextcord never calls `cog_load`, and calls `cog_unload` **synchronously**. Put async startup in `async def cog_ready(self)` (called from `on_ready` after the DB is up, and after `/admin reloadcog`; a hook that **raises** is retried with backoff by the health check until it succeeds, so raise when the work couldn't be done and keep hooks idempotent); keep `cog_unload` sync and `spawn` any async cleanup. `tests/test_lifecycle.py` enforces this.
- **Images:** CPU-bound Pillow work (`src/utils/card_generator.py`) runs in `asyncio.to_thread(...)`.
- **Config:** single `.env`. `DATABASE_URL` or individual `POSTGRES_*` vars. Comma-separated ID lists: `ADMIN_IDS`, `OWNER_IDS`, `FOUNDER_IDS`, `STAFF_IDS`, `INTERN_IDS`, `DONATOR_IDS`, `ACTIVE_PRO_IDS`.

## Content policy — flag haram or shady features (all agents)

VEKA is a professional community with members of many faiths, run by a Muslim owner. Keep the bot **halal and religion-neutral**. Before adding, enabling or extending anything below, **stop and flag it to the user** with what it does and why it's flagged, and wait for an explicit go-ahead. Never add it silently, and never "just make it configurable" as a workaround. Also flag existing code in these categories when you come across it.

- **Music and instruments:** music streams/stations, song playback, music bots, music leaderboards or promotion (e.g. top songs/artists).
- **Gambling and chance-for-value:** betting, casino games, slots, coinflip/roulette for currency, lotteries, raffles you pay into, loot boxes, wagering XP/coins.
- **Riba (interest) and shady finance:** interest-bearing loans or savings in any economy, crypto/NFT pump schemes, trading "signals", MLM/referral pyramids.
- **Intoxicants and immoral content:** alcohol, drugs, NSFW/sexual content, dating/flirting features, vulgar humour commands.
- **Religious promotion:** pushing any religion (including Islam) on the whole server, e.g. auto-playing recitation or forced religious messages. Opt-in, user-requested features are fine. Ask when unsure.
- **Shady/privacy-invasive behaviour:** tracking or logging members without clear opt-in (presence/activity/listening history, DMs, IPs), scraping personal data, self-bots or Discord ToS evasion, dark patterns, deceptive impersonation, hidden data sharing with third parties.

Decided 2026-10-11: presence tracking is opt-in (`/privacy`) and Spotify/listening tracking and `/most listened` are removed. Previously flagged (2026-10-06): Spotify listening tracking and the `/most listened` Spotify songs/artists leaderboard (`src/cogs/rpg/rpg_manager.py`, `src/cogs/stats.py`) are music promotion and track members without explicit opt-in. Presence-based game/app tracking (RPG activity) has no opt-in either.

## Notable subsystems

- **Honeypot** (`src/cogs/admin/honeypot.py`): trap channels that punish non-bot, non-webhook posters (`softban`/`ban`/`timeout`/`role`/`log`). Per-guild cooldown from `guild_settings.honeypot_cooldown_seconds`. Acts first (ban/softban purge server-side via `delete_message_seconds`, 0–7 days); timeout/role actions get a bounded bulk purge in the background. Members with Manage Messages/Administrator, the owner, and anyone at/above the bot's top role are exempt (logged as `exempt`). Channel config is cached in memory and not invalidated on external DB changes.
- **Mass unban** (`src/cogs/admin/massunban.py`): admin-only, double confirmation, `preview` subcommand, resumable DB-backed jobs (`massunban_jobs`, `massunban_job_items`), sequential unbans (one `unban` call per user; 404 = already unbanned) with one worker per job (lock) and 429 pause/resume, resumes interrupted jobs in `cog_ready()`. The command defers and the job runs as a background worker. **Outbound:** one edited progress message in the log channel (IDs persisted in the job, so a restart keeps editing it), one final summary DM to the runner, failures as one attached file. Apology DMs are **off** unless `notify_users:true` / `--notify`; then only users who still share a server with the bot, max 50/job, ≥5 s apart, stopped after 5 failures in a row; counts shown in preview/confirmation. (The bot was quarantined once by the old send-a-DM-to-everyone behaviour.) A 403 stops the job (`failed`, reason in `metadata.forbidden`) and leaves the remaining items pending; error 60003 means the server requires 2FA for moderation and the bot owner's account has no 2FA. Every ban is recorded in `audit_logs` (`ban_executed`) by the `on_member_ban` listener. **Limitation:** Discord's ban list has no timestamps or moderator, so date/moderator filters only match bans the bot recorded; unaudited bans are **excluded** unless `include_unaudited:true` (slash only, never with a moderator filter). Selection logic: `match_bans()`.
- **Honeypot alerts** are raid-safe: the first trigger per guild posts the alert (with the role ping); further triggers within 60 s become one digest without a ping. **Welcome** switches to one batched message (no cards) when a guild gets more than 5 joins/min. **Inactivity**: one daily digest in the log channel; "we miss you" DMs only if `guild_settings.inactivity_dm_enabled`. **Squad ping**: once per guild per 10 min.
- **Maintenance** (`src/cogs/admin/maintenance.py`): nightly retention at 03:30 UTC — `user_activity_log` 90 d, `honeypot_events` 180 d, items of mass-unban jobs finished 180 d ago, images of listings withdrawn 30 d ago (`RETENTION_*_DAYS` env overrides). Never deletes aggregates (`users` totals, `user_activity_daily`), `audit_logs`, or `feed_seen_items` (dedupe IDs live as long as their subscription; age-based deletion would repost static feeds).
- **Marketplace** (`src/cogs/marketplace/*`): listings are global; publication goes only to the invoking guild's `/setup marketplace` channel (text or forum; no global fallback), recorded in `marketplace_publications` (idempotent per guild/listing; a Discord-send→DB crash can still duplicate once). Member-created posts in that **forum** are ingested silently (`source='forum'`, `thread_id`): price parsed only from explicit currency (`$123`, `123$`, `USD 123`, `123 USD`), otherwise `NULL` + `pending_review`; tags → category; starter edits update; archive/lock → `archived`, reopen reactivates (never resurrects `withdrawn`); delete → `withdrawn` (nextcord only reports deletes of cached threads). Bounded backfill (100 unknown active threads/boot). Manual forum posts are not mirrored to Directus. All `/marketplace` commands remain. `!marketplace_sync`/`!marketplace_push` are bot-operator only, max 25 per run. **Images**: Discord CDN links expire (~24 h); `src/services/marketplace_images.py` stores up to 4 normalised WebP copies per listing in PostgreSQL (`marketplace_listing_images`, EXIF stripped, ≤1600 px, ≤2 MB) and bot posts attach the stored file (`attachment://`). Old copied URLs without a source message are unrecoverable (`image_missing`).
- **Moderation** (`src/cogs/admin/moderation.py`): `warnings` table (snowflake `BIGINT` columns since 022) with auto-escalation to mute/ban at per-guild thresholds; role-hierarchy checks (`_hierarchy_refusal`); escalations write `audit_logs`; `/modstats` reads `warnings` + `audit_logs`.
- **RPG/activity** (`src/cogs/rpg/rpg_manager.py`, `src/services/activity_service.py`): every award (messages, commands, voice/presence minutes) is **one SQL statement per batch** (`activity_service.award`) that adds the real quantity to the global `users.total_*` column and the per-guild `user_activity_daily` row for the UTC date, adds XP (`max(1, floor(base × role × streak multiplier))` per input row, so each server keeps its own multiplier and rollup), and derives the effective streak (expired → no bonus), the multiplier and the level from the **locked** users row. Presence metrics and named details are written only if the server switched tracking on (`guild_settings.presence_tracking_enabled`, joined per row in the SQL) and `presence_opt_in` (= "tracking allowed", default **true**, false after `/privacy optout`/`delete`) is true on that locked row; `/privacy delete` locks the same row first, so a tick collected before an opt-out can't write afterwards. A tick (all metrics + details) is one transaction (`award_tick`). Messages (10 s cooldown, `TTLDict`) and commands (`on_application_command_completion` / `on_command_completion` — nextcord has **no** `application_command` event) award as they happen. Voice and presence are **sampled** by `activity_tick` every minute from the gateway cache: no in-memory sessions, so restarts lose ≤1 min and members already in voice/playing at startup count. Voice rules: AFK channel or deafened → nothing; alone (no other non-deafened human) → minutes, no XP. Message counts are XP-eligible messages (10 s per-user cooldown). Presence is credited once per minute to one guild (main guild preferred) for the per-guild rollup. The first tick after start credits nothing (restart loses ≤1 min); the 60-minute XP cap is per process. Missed season archives are recovered daily/on start (announced only in the first 3 days). XP is capped at 60 continuous minutes per kind; totals never are. Presence (games, coding apps, streaming; coding apps are not gaming): **server opt-in + member opt-out** (owner decision 2026-10-11) — only in servers whose admins enabled it (dashboard or `/setup option presence_tracking on`, off by default), skipping members who ran `/privacy optout`; listening/Spotify is never tracked (content policy, confirmed by the owner). `user_activity_log` is no longer written (retention purges it). Leaderboards inside a server are **always per server** (all time = everything recorded in that server) from `user_activity_daily`; global totals (`users.total_*`, XP/level) remain for `/level`, `/rank`, `/activity stats` (labelled "all servers"). Every server gets its own auto-leaderboard (`/setupleaderboard`, Manage Server; message ID in `guild_settings.leaderboard_message_id`), activity roles (roles named Active Member/Active+/Active Star, thresholds on XP earned *in that server*, removed after 14 days without activity there, unsafe roles skipped), daily inactivity digest (`inactivity_alerts_enabled`, on by default, needs a log channel; per-server markers in `inactivity_notices`), and season announcement (`season_announcements`). Seasons = UTC calendar month, snapshotted per server (`leaderboard_snapshots`, completion marker `season_archives`).
- **Privacy** (`src/cogs/privacy.py`): `/privacy status|optin|optout|delete` (+ `!privacy …`). Delete (button-confirmed) removes the member's activity rows and snapshots and resets XP/totals/streak in one transaction, and is audited.
- **Radio** (`src/cogs/radio/radio.py`): **disabled** (commented out of `EXTENSIONS`; `tests/test_cog_loading.py` and `tests/test_permissions.py` still load it so it doesn't rot). It has no built-in stations: music stations were removed (content policy), and religious stations were left out to keep the bot neutral. Admins `/radio podcast <feed> [episode]` (RSS enclosure, newest = 1) or `/radio play <url>` (any public audio URL; prefix `!radiopodcast`/`!radioplay`). The bot joins the radio channel, plays, and leaves when the audio ends or fails. User URLs are pre-checked by `resolve_public_media_url` (http/https, public DNS only), and FFmpeg runs with `-protocol_whitelist http,https,tcp,tls,crypto`. A per-play generation counter keeps an intentional `stop()` from being treated as "finished". No yt-dlp, so YouTube/Spotify links don't play.
- **Feeds** (`src/cogs/resources/feeds.py`, `src/services/rss_service.py`): DB-backed `feed_subscriptions`; dedupe per subscription in `feed_seen_items(subscription_id, item_guid)`. User-supplied URLs are fetched only through `src/utils/http.fetch_public_url` (http/https only, public IPs only via `PublicOnlyResolver`, redirects re-checked, 2 MB cap). `/feed add|edit|pause|resume|remove|test` need Manage Server; `feed_url` options autocomplete from the server's subscriptions. Outage state (`consecutive_failures`, `next_retry_at`, migration 027) is persisted per subscription: one warning at three failed polls, one recovery notice, exponential retry backoff capped at one day (never shorter than the configured interval). Failed attempts also update `last_polled_at`. Manual fetch/test calls do not send admin alerts. Migration 028 adds `paused` and removes only unconfigured historical seeds; configured subscriptions survive. One-minute scheduler honors 10–1440 minute intervals; `/feed list [page]` shows health and channel availability, 10 entries/page. Limits: `FEED_MAX_SUBSCRIPTIONS` (25/server including paused), `FEED_MAX_POSTS_PER_POLL` (3/feed), `FEED_MAX_POSTS_PER_GUILD_PER_CYCLE` (15/server/cycle). Quota checks are serialized in the single bot process; do not run multiple pollers.

## CI/CD

- **`.github/workflows/ci.yml`** runs on every pull request, as a reusable workflow (`workflow_call`), and manually. Jobs: `checks` (ruff lint + format check, mypy, pytest with a PostgreSQL 17 service (`VEKA_TEST_DATABASE_URL`), `pip-audit` on the locked runtime deps (PyNaCl advisories ignored, reason in `ci.yml`)) and `docker-build`. Keep mypy at zero errors. Superseded PR runs are cancelled. The concurrency group is keyed by PR number or SHA, never by `github.ref` alone: a `pull_request` run queued after its PR merged reports the base branch as its ref, and once cancelled the run on `main`.
- **`.github/workflows/deploy.yml`** runs on every push to `main` (i.e. every merged PR) and manually (`gh workflow run Deploy --ref main`). It calls `ci.yml` as the gate, then runs the `deploy` job on the self-hosted runner (`self-hosted, X64, Linux, Veka`) in the `production` GitHub Environment (deployment history; approvals/environment secrets can be added there). Deploys are serialized and never cancelled mid-rollout. The job writes `.env` (mode 600) from secrets (`DISCORD_TOKEN`, `DATABASE_URL`, …) and variables (`ADMIN_IDS`, `OWNER_IDS`, `ADMIN_ALERT_CHANNEL_ID`, `LOG_LEVEL`, …), passing them through `env:` and never interpolating them into the script. It runs `docker compose build`, then `docker compose up -d --force-recreate` (bot + dashboard API), and passes only if `"is ready. DB available=True"` appears in the bot logs within 60s and the API's `/v1/ready` returns 200 within 60s. It emits a warning annotation if the bot line says `migrations=degraded`.
- Actions are pinned to commit SHAs (with a version comment); `.github/dependabot.yml` bumps them monthly against `dev`.
- Development happens on `dev`; open a PR `dev` → `main` to deploy. Anything that lands on `main` deploys, so `main` should be protected (PR required, `CI` checks required).

## Known issues (open)

1. The SvelteKit dashboard migration onto the bot API is in progress in `wt/dashboard-web`; shared plan/reviews live in the parent workspace's `.agent-notes/dashboard/`.
2. The container still runs as root: the deploy mounts `.env` with mode 600 for the runner user, so a non-root user needs a deploy change first.
3. `_is_staff_user` in `safety.py` fakes a context with `SimpleNamespace` to call RBAC — fragile coupling.
4. `runtime_state.alert_state_cache` is still used ad hoc for export progress.
5. Historical `total_streaming_minutes` stay inflated by the old double count (no record to repair from).
6. `mentorship_matches` is a read-only archive of the old model; binding legacy mentorships to a server needs explicit staff action (not built).
7. Mass-unban date/moderator filters only match bans the bot recorded (Discord's ban list has no dates or moderators).
8. Unique constraint on `profiles.user_id` is duplicated across migrations `005` and `006` (harmless).
